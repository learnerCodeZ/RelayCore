## 1. 发布判断

**建议先修复四项 P1 问题，再邀请外部用户内测。当前更适合维护者在可恢复的测试项目上自测。**

项目已有较完整的本地授权、任务持久化、候选与快照绑定、审查隔离、源文件冲突检查和整合备份。它并非只剩界面包装，也不需要为本次内测先建设多租户、云部署或复杂插件架构。

现在的主要缺口是：几个跨步骤、跨任务、跨进程的状态边界仍不可靠。完整测试通过，仍可在补充夹具中复现“两个整合都成功却发生覆盖”“回滚半途停止后状态仍正常”等问题。继续增加模型能力应排在这些修复之后。

没有在本次范围内确认绕过每任务授权的漏洞。这个结论不等于完成渗透测试，也不适用于公网、多用户或恶意同账号进程的场景。

### R1：整合锁只覆盖单个任务，不能保护项目文件

**证据：** `src/core.mjs:827–834` 以 task ID 为锁键；`src/core.mjs:876–882` 在异步读取检查后写入源文件。两个任务的锁互不影响。

**触发：** 两个已完成、拥有相同源基线的任务，都修改 `message.txt`，并同时调用 `integrateWorkspace`。在已验证的交错中，两个调用均成功并分别记录 `integration.completed`，最终文件却只保留其中一个候选结果。

**影响：** 后一个写入可覆盖另一个已经报告成功的整合。网页双击不同任务按钮、多窗口或 CLI 与网页并用，均可能产生并行请求；单用户不等于没有并发。

**建议：** 当前项目每次只允许一个整合或回滚操作进入完整的“校验→备份→写入→记账”流程。先用项目级串行锁，保留原有基线与逐步冲突检查；不必立即实现复杂的细粒度锁。这只能解决 RelayCore 自身并发，外部编辑器的检查后写入窗口仍需明确边界。

**验收：** 两任务同路径并行整合只能一个成功，另一个因源基线冲突失败；不相交路径的请求也可先串行；整合与回滚交错不会覆盖彼此；不得出现两个成功事件掩盖同一基线下的丢失更新。

### R2：回滚中断未被启动对账覆盖

**证据：** `src/core.mjs:929–946` 逐个恢复文件，最后才写回滚完成事件；普通异常会进入 `RECOVERY_REQUIRED`，但进程被强制终止时不会执行 catch。启动检查在 `src/core.mjs:1237–1238` 发现任何旧的 `integration.completed` 等事件就跳过。

**触发：** 任务已成功整合两个文件；回滚恢复第一个文件后进程终止，第二个文件仍是整合后的内容。以此磁盘和日志现场重启，任务仍显示 `COMPLETED`；重试回滚则因首个文件不再匹配 after hash 被拒绝。

**影响：** 项目处于 before/after 混合状态，系统却没有主动标记需要恢复，用户可能误以为任务状态正常。备份仍在，不等于恢复流程已经可靠。

**建议：** 写源文件前持久化 `rollback.started` 或等效操作记录；完成后写终态。启动时对“有开始、无终态”的回滚依据 manifest 和文件 hash 对账；混合状态进入 `RECOVERY_REQUIRED`，保留备份并给出人工核对路径。不要自动覆盖无法确认归属的用户改动。

**验收：** 在恢复第一个文件前、文件之间、全部恢复后但终态记账前，分别模拟中断并重启；能够区分未开始、已完成、混合或外部修改。**现有首次整合中断对账已存在，不应为修复此项把它删除重写。**

### R3：生产入口提前拒绝已应用提案的暂停任务

**证据：** `src/daemon.mjs:47–49` 对已有候选先调用 `verifyWorkspace`，要求它仍等于原始基线；`src/dsh.mjs:117–122` 才包含处理候选已变化的刷新逻辑。

**触发：** DSH 提案已应用到候选，审查尚未完成时暂停。仍在原授权与累计预算范围内恢复，生产入口先抛出 `Workspace file changed`，后续安全刷新逻辑到不了。临时夹具复现 `PAUSED → RECOVERY_REQUIRED`，失败发生在任何真实模型调用之前。

**建议：** 把恢复准备集中在一处，明确先核验源基线、候选登记、授权和剩余预算，再处理允许的中断候选。不要用“删掉所有验证”来让恢复通过。恢复后重新执行会消耗剩余回合，这项成本应在界面中说明。

**验收：** 覆盖提案前、提案应用后、审查中三个暂停点；在源未变化且预算充足时可恢复；源冲突或预算不足时返回准确原因，不误报为工作区异常；不继承额外预算、不重复整合。

### R4：自动侧栏登记可能覆盖 DSH 较新的工作区索引

**证据：** `src/dsh-workspace.mjs:20–46` 读取整个 `~/.dsh/storages/workspace.json`，修改一项后整体替换；`src/dsh.mjs:147–149` 在账户执行路径自动调用。代码注释已承认 DSH 同时在内存维护并整体写回，但没有双方参与的并发协议。

**复现：** 在 RelayCore 读取后、替换前，模拟 DSH 新增另一个工作区。登记返回 `attached:true`，RelayCore 会话成功加入，但另一方新建的工作区索引记录消失。

**影响边界：** 丢失的是索引更新和侧栏可见性；本次没有证明会话归档本身被删除。这里涉及用户原有 DSH 数据，不能只解释为 RelayCore 自己的条目可能掉失。

**建议：** 内测默认关闭自动写外部注册表，使用已有 RelayCore 会话查看页面。以后若通过官方接口或双方认可的并发协议实现，再恢复此便利功能。只给 RelayCore 自己加锁、或在写前再读一次，仍不能消除 DSH 随时写入的竞争窗口。

**验收：** 默认执行任务不写入 DSH 的全局索引；需要启用时必须证明并发更新不会被覆盖，失败也不损坏或覆盖原文件。

### R5：环境变量无法覆盖配置文件以关闭执行

**证据：** `src/daemon.mjs:20–23` 分别计算环境和配置文件的启用条件，只要其中之一为真就开启。与上方“环境变量优先，其他值保持关闭”的说明不一致。

**复现：** `RELAYCORE_EXECUTION=disabled`，同时配置 `execution: 'account'` 及必需路径，仍返回已启用的 executor。

**影响边界：** 应急关闭可能产生误判；仍需每任务授权，**不是直接未授权执行**。

**建议与验收：** 先根据变量是否明确存在决定是否读取配置，定义清晰的 `off` 值，未知值拒绝启动。覆盖“env off + config account”“env account + config off”“未设置 env”三组测试，并让启动信息显示最终模式和配置来源，不输出秘密。

### R6：自检与实际运行配置不一致

**证据：** README `110` 行推荐无参数 `node src/doctor.mjs`；`src/doctor.mjs:24–31` 却只读位置参数里的 DSH 路径，不读网页保存的配置，也不读同等运行环境配置。本次无参数执行明确失败。`45–48` 行把无代理算失败，`50–57` 行把端口能否绑定当成功标准。

**影响：** 正常安装或已启动的用户也可能被报告失败；开发机上的代理假设会被传播为用户必需条件。

**建议：** 自检复用生产配置解析。必要依赖失败、可选代理警告、已正常运行、被其他程序占端口分开显示。补充 SDK 原生程序和两侧登录材料的无模型可用性检查，不以“文件存在”声称远端登录有效。

**验收：** 网页保存配置后无参数诊断能识别相同路径；无代理但可以直连不构成安装失败；正常运行的本服务不被报为端口安装失败；不调用模型、不打印口令或带凭据的代理 URL。

### R7：会话查看的同步读入与解压没有资源上限

**证据：** `src/daemon.mjs:85–94` 在服务主线程同步读取、解压、拆分并解析整个会话；`105` 行才截断展示文本。展示截断不能限制之前的内存分配和阻塞。

**判断：** 这是静态确认的资源控制缺口，尚未做真实大归档压力测试，不能描述为已发生崩溃或公网攻击。

**建议与验收：** 读取前检查压缩／原始文件大小，限制解压后的总数据，超限给出可读错误；先提供尾部或分页查看。若仍需处理大归档，再移到工作线程。验证损坏归档、超限归档，并确保查看期间暂停／停止操作仍有响应。

### R8：把当前可运行仓库变成可追溯的内测版本

**事实：** `package.json:3–4` 是 `0.1.0`、`private: true`；当前没有 Git tag，也没有已跟踪的 CI 工作流。锁文件和安装说明已经存在，不需要重新引入一套包管理方案。DSH 接入依赖其包内路径，兼容性仍需逐版本核实。

**建议：** 用固定 commit/tag 发放内测包，附 Windows、Node、DSH、SDK 版本和安装命令；最小 CI 只需锁定 Node，执行干净依赖安装和有时限的无模型测试，不接入真实账号。公开分发前决定许可证；没有 LICENSE 不妨碍私下约定试用，但不等于已授予公开再分发许可。

**验收：** 由一位未参与开发的人在干净 Windows 用户环境，从固定版本完成安装、配对、两侧登录、自检，经费用同意后完成一个真实任务，再整合、回滚。记录脱敏证据。开发机 156 项测试不能替代这一步。

### R9：明确“审查通过”和“已经落地”的区别

**证据：** `src/daemon.mjs:55–56` 的生产组合未传 `verifyCandidate`；`src/dsh.mjs:156–169` 允许没有确定性检查证据的模型批准并写出 handoff。当前完成状态对应审查完成，界面 `src/daemon.mjs:340–341` 再提供整合和回滚按钮。

**判断：** 模型审查是已有产品机制，不应把“没有自动跑任意测试”说成授权漏洞。但它不能支持“验收标准已被确定性证明”的强结论，也不能让用户把 `COMPLETED` 当作源项目已更新。

**建议：** 最小改动是显示“审查通过，待整合／已整合／已回滚”，显示是否有候选检查证据；对精确文本、JSON 格式等受支持场景增加宿主实现的确定性检查。未实现的检查明确显示未验证，不要自动运行模型提议的命令来填补空白。

另一个直接影响内测支持的缺口是 `src/core.mjs:1167–1174`：执行异常详情只写 stderr，持久事件通常只记录 `task.recovery_required`。应保存长度受限、脱敏的错误类别和原因，重启后仍能查询；不要把完整模型请求或凭据写进错误记录。

**验收：** 用户无需翻日志即可知道文件是否已写回、是否可回滚、通过的是哪些检查；`ready` 加 LF 之类任务可以由字节检查给出证据；保留审查快照和 hash 绑定；失败后重启仍有可操作、已脱敏的原因。

### R10：快速开始、恢复演练与反馈材料一起收口

**事实：** README `102` 行说自动打开浏览器，`104` 行及实际实现却要求 `RELAYCORE_OPEN=1`；`20` 行的架构文档链接目标不存在；若干阶段表与后续真实验收记录未同步。独立 Codex 审查登录是必要条件，应进入主快速开始。

**已有优点：** README `116–120` 已说明停机备份、SQLite WAL 一致性和敏感材料，不应报告“没有备份方案”。缺少的是本次能核实的完整恢复演练。

**建议：** 首页只保留当前事实和一条受支持路径，历史阶段状态移到归档。记录一次同机同账号的备份恢复；跨机器／Windows 账号时明确 DPAPI 口令与登录资料不能直接视作可用，应重新建立身份与授权。反馈模板收集固定版本、诊断摘要、任务 ID、脱敏错误和最小复现，默认不要求发送整个 `.RelayCore/`、DSH home 或原始会话。

**验收：** 文档链接检查通过；新用户只看快速开始即可完成支持路径；隔离恢复后任务与事件可读、候选和快照 hash 可核对、运行中状态需人工确认，不能自动覆盖原文件。

## 4. 最小发布门槛与实施顺序

建议按以下顺序推进，每一步都有可验收结果，不以“补了很多代码”作为完成标准：

1. **先保护用户数据：** 默认关闭外部 DSH 索引写入；项目级串行化整合与回滚；补回滚中断对账。
2. **再让任务状态可信：** 修复生产暂停恢复顺序；保留授权、源冲突及累计预算检查；让关闭执行开关明确有效。
3. **让安装可复现：** 自检与配置统一，清理主指引，生成固定内测版本；补最小 CI 回归。
4. **最后做发放演练：** 新用户干净环境跑一次获同意的真实链路和撤销流程，记录恢复演练，再发送邀请。

发放前至少满足：

- [ ] R1–R4 有对应修复和正式回归，补充复现脚本不再触发缺陷。
- [ ] 原有完整回归仍全部通过，既不降低安全断言，也不靠 skip 隐藏失败。
- [ ] 已验证关闭执行、自检、过期授权、预算不足、源冲突均返回准确状态。

## 5. 内测范围与主动提醒

首轮只支持非敏感、可恢复的小型 UTF-8 文本项目，保持用户手动授权、手动整合；不把任务目录或 `allowedPaths` 宣称为 OS 沙箱。不开放公网，不把多人共享同一控制口令纳入支持范围。

费用的现实边界仍是显式同意、时长和模型回合预算；一次提示内部的远端循环、取消后的远端消耗和金额硬封顶没有因此解决。邀请材料应直说这点，并使用较小的单任务额度；不要把“停止按钮已点下”当作账单已经停止。

错误报告和会话查看会接触项目内容与账号信息，内测支持不应以获取用户完整目录为前提。依赖 DSH 非公开内部路径意味着上游升级可能破坏接入；固定支持版本、先做兼容验证，比现在建立通用适配器更合适。

本轮不建议优先建设云控制面、多租户、插件市场、复杂消息系统或大规模重构。`core.mjs` 与 `daemon.mjs` 较集中确有维护成本，但应先用上述回归把关键行为固定，再按真实修改需要拆分。
